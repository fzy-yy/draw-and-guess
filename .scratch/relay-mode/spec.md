# 接龙模式（传话接龙 / Relay Mode）实施规格

Status: ready-for-agent

> **设计共识（唯一权威）**：[`consensus.md`](./consensus.md)（S1–S86 + §三 玩法汇总 / §五 架构 / §七 治理 / §八 顶栏与复盘编排）。

## Problem Statement

现在只有**经典模式**（轮流当画家、一轮一题）：玩家各自猜同一张画，玩法单一，玩久了缺少「传话走样」这类会自然长出来的笑点；
而且房间规则里还有一批长期没人用的开关（观战 / 下一局加入 / 可调人数上限），让房间列表、席位与快照裁剪逻辑比实际需要复杂得多。

具体到玩家侧的感受是：

- 想换个玩法只能重开一个「轮流画」的房间，没有第二种玩法可选；
- 房间满员规则是房主手调的，常常出现「点了开始也没人够」的空转房间；
- 观战 / 下一局加入这两个入口几乎没人用，却让席位与加入流程多出很多分支。

## Solution

在**建房时**增加第二种玩法「**接龙模式**」：N 名玩家同时开启 N 条平行链，每条链固定 **4 步**（画 → 猜 → 画 → 猜），环状顺延，
每步全员各对自己负责的那条链动手一次；四步走完后全员一起按链自动复盘（重播 → 揭晓 → 接着重播 → 揭晓），
每条链末尾投票判定「这个匹配吗？」，按赞同票数给该链参与者加分；全部链走完进入终局战报。

同时借这次改动把房间里两个长期无人使用的入口（观战 / 下一局加入）与可调人数上限**一并删除**，容量固定 6 人、开局后不可加入。

玩家在接龙模式下**只能看到自己当前这一棒需要看到的东西**（上家的画或上家的答案），自己画的画在交给下家之前对其他人完全保密；
作答与聊天彻底分开：作答保密、聊天自由。

## User Stories

**房间与开局**

1. 作为房主，我想在建房弹窗里选「经典模式」或「接龙模式」，这样我不需要靠额外说明就能确定这一局玩什么。
2. 作为房主，我想在建房时就定死玩法、房间内不能改，这样中途不会有人把玩法改掉导致对局作废。
3. 作为任意玩家，我想在房间头部看到当前模式徽标（经典 / 接龙），这样我进房就知道这局玩什么。
4. 作为任意玩家，我想房间容量固定为 6 人且不能再被房主调整，这样我不会遇到「房间只开 2 个位子」这种永远开不了局的死房间。
5. 作为房主，我想在接龙模式下「开始游戏」按钮在**在线可玩人数不足 4 人**时置灰并给出原因，这样我知道还差几个人。
6. 作为房主，我想在**全员准备**后才能开局，这样不会有人还没回来就被拖进对局。
7. 作为任意玩家，我想开局之后大厅与私密码两种加入入口都置灰显示「游戏中」，这样我不会误以为还能挤进来。
8. 作为任意玩家，我想观战与「下一局加入」入口彻底消失，这样界面里不会再出现我永远用不上的选项。
9. 作为房主，我想在等待阶段仍能改接龙规则（选词/作画/猜词时长、候选词数、换一批、自定义题目、房间内邀请），这样我能按人数调节奏。
10. 作为房主，我想规则弹窗只显示接龙下真正生效的字段，这样我不会去改一个改了也不生效的开关。
11. 作为房主，我想接龙房间只列出 4/5/6 的容量语义（容量固定 6，但开局门槛是 4），这样我不会建出一个开不了局的低容量房。

**四步链与动手**

12. 作为玩家，我想在接龙里和所有人**同时**开始，这样没有「等别人画完我才能动」的垃圾时间。
13. 作为第 1 棒的玩家，我想进入独立的选词阶段并从我自己的候选词里挑一个，这样我能画自己会画的题。
14. 作为第 1 棒的玩家，我想在选完词后立刻开始作画（不额外等待），这样节奏不拖沓。
15. 作为玩家，我想在步骤 1 看到自己选的词作为题面，这样我知道自己在画什么。
16. 作为玩家，我想能「换一批」候选词，想「自定义题目」时也能直接输入，这样我总有办法开工。
17. 作为玩家，我想在选词倒计时结束时由服务端**随机替我选一个词**继续（而不是交空白画布），这样我的链不会因为走神而变成一张白纸。
18. 作为第 2/4 棒的玩家，我想看到上家**最终提交的那幅画**（静止呈现、只读），这样我能专心猜。
19. 作为第 3 棒的玩家，我想拿到上家**猜出来的那句答案文本**作为我的题面（并看不到他上一步的画），这样链条会真的走样、也才好玩。
20. 作为玩家，我想在猜词时用画布底部的一个**可拖动输入浮层**提交答案，这样浮层可以拖开不挡住我要看的画。
21. 作为玩家，我想在猜词时看到上家是谁（头像 + 昵称，且因为我看的是他的画而带一个画笔角标），这样我知道我在看谁的画。
22. 作为玩家，我想在按上家的词作画时也能看到上家是谁（但**不带**画笔角标，因为他没有画东西给我），这样角标语义始终是「这段里谁动笔画了」。

**提交、锁定与代交**

23. 作为玩家，我想点了「确定提交」之后立即锁定、不能撤回修改，这样全员的进度是可预期的。
24. 作为玩家，我想在提交后看到「已提交，等待其他玩家」的状态，这样我知道自己不用再等自己。
25. 作为玩家，我想在**全员提交**时立即取消剩余倒计时进入下一棒，这样不会全员都交完了还在干等。
26. 作为玩家，我想在猜词时**不能提交空白**（输入为空时提交按钮置灰），这样链上不会出现无意义的空答案。
27. 作为玩家，我想猜词输入框沿用与聊天一致的 60 字上限，这样长答案不会被截断得莫名其妙。
28. 作为掉线的玩家，我想在 20 秒内重连还能接着当前这一棒继续，这样网络抖一下不至于直接报废。
29. 作为掉线/离开的玩家，我想我的链位仍然保留、由服务端按规则自动代交（作画=已有笔画，猜词=输入框内容、为空则填「？」），这样别人的链绝不会因为我不在而断掉。
30. 作为仍在场的玩家，我想在有人掉线时不必等他，倒计时或宽限期一到就推进，这样少数人的网络问题不会拖住全房。
31. 作为玩家，我想在可玩人数掉到 4 以下时本局仍能正常走完并按已有分数结算，这样不会因为有人退房就整局作废。

**保密与可见性**

32. 作为玩家，我想**只**看到自己这一棒需要看到的内容（自己的候选与画布、或上家的画、或上家的答案），这样我无法提前知道别的链在发生什么。
33. 作为玩家，我想我的作答内容在揭晓前**完全保密**（不进聊天流、不给其他玩家任何提示），这样链的悬念成立。
34. 作为玩家，我想聊天是**独立的社交频道**，不会把我的作答带出去，这样我能和大家吐槽而不泄露答案。
35. 作为玩家，我想每个步骤结束后服务端才把内容交给下一棒玩家，这样链条的保密性由服务端保证而不是靠客户端自觉。

**复盘与投票**

36. 作为玩家，我想四步走完后全员**统一步调**进入复盘，这样我和别人看到的进度永远一致。
37. 作为玩家，我想复盘按**链发起人的席位顺序**逐条展示，这样顺序是确定且可预期的。
38. 作为玩家，我想每条链里先看第一棒画家的画作重播、再揭晓第二棒的答案，然后看第三棒的画作重播、再揭晓第四棒的答案，这样一条链的前因后果我能完整看懂。
39. 作为玩家，我想在复盘顶栏看到「谁画 → 谁猜」的两个头像昵称（画家带画笔角标、猜词者不带），并且这两个位置**全程不移动**、只有答案在动，这样我的视线不会跟着头像乱跳。
40. 作为玩家，我想未揭晓的答案用和经典模式一样的**下划线占位**，这样我不会把一个问号误认成真的答案。
41. 作为玩家，我想复盘是纯自动的：不提供跳过、也不能提前结束，这样不会有人把别人的链跳掉。
42. 作为玩家，我想复盘期间有人掉线或离开也不影响轮播继续，这样展示不会卡住。
43. 作为玩家，我想看到「第 k / N 条链」的进度写在顶栏最左侧标签后面，这样我知道还剩几条。

**投票与计分**

44. 作为玩家，我想在每条链末尾对「初始词与最终答案是否匹配」投**赞同 / 不赞同**（只有这两项），这样判定足够简单。
45. 作为玩家，我想投票点下就锁定，这样不会出现有人看到风向再改票。
46. 作为玩家，我想票行按**到达顺序匿名**实时插入 ✔/✘，这样过程是公开的但不显示「谁投了什么」。
47. 作为玩家，我想左侧玩家面板显示每个人「已投票 / 未投票」，这样我知道还差谁。
48. 作为玩家，我想投票**一律等满 10 秒**（即使所有人都投完也不提前公布），这样断线的人始终有完整的时间补投。
49. 作为玩家，我想**没有弃权**：倒计时结束仍未投的人算作「不赞同」，这样阈值不会被「少几张票」变相放宽。
50. 作为玩家，我想链获得「赞同票多于反对票」才算匹配成功，成功后该链 4 名参与者**每人加 赞同票数 × 10 分**，这样「越多人认可、大家都赚得越多」。
51. 作为玩家，我想匹配失败时该链参与者本链得 0 分，这样判定是有代价的。
52. 作为参与者，我想我参与过的每条链都能给我带来分数，这样多链并行不会有人被落下。

**对局期管理**

53. 作为房主，我想在对局期（选词/作画/猜词）可以「提前结束本局」逃生，这样房间卡住时我能出来。
54. 作为房主，我想提前结束时直接进终局并按**当前已产生的分数**结算（接龙里没有投票，因此全员 0 分），战报如实记下「房主提前结束」，这样结算口径不会撒谎。
55. 作为玩家，我想「主动退出本局」仍然保留我的一张冻结成绩卡并留在榜单里（链位由服务端代交），这样我的成绩仍属于本局历史。

**终局战报**

56. 作为玩家，我想在全部链展示与投票完后看到最终排名与分数，这样我知道这局谁赢了。
57. 作为玩家，我想终局沿用经典模式的结算版式（奖杯圆底 + GAME RESULT + 最终排行 + 逐行名次/头像/昵称/分数 + 再来一局/退出房间），这样两套玩法看起来是一家人。
58. 作为玩家，我想行内第二行显示**接龙口径**的统计（参与 N 条链 · 共获 M 张赞同票），而不是经典模式里那些在接龙下根本不存在的「猜中次数/平均秒数」。
59. 作为玩家，我想终局**不显示荣誉称号**，这样不会出现「用不存在的数据算出来的称号」。
60. 作为玩家，我想「再来一局」保持接龙模式继续下一局（模式只允许在建房时改），这样连打时不用重建房间。

**可维护性（开发者视角）**

61. 作为维护者，我想接龙与经典的差异都通过**改造原组件 + 插槽/props**表达（经典不传新数据时行为与现状完全一致），这样不会出现两套需要永久同步的 UI。
62. 作为维护者，我想接龙的互不相同的四个组件共用同一份「玩家 chip」，这样角标与排版只有一处定义。
63. 作为维护者，我想服务端接龙状态机与经典回合状态机**平级并存**、由装配层按模式委托，这样经典的那批回归测试完全不受影响。
64. 作为维护者，我想所有新时长/阈值/动画参数都落在既有配置包里、所有新文案都进文案包，这样不会有魔法数字与硬编码中文散落在组件里。

## Implementation Decisions

### 协议契约（`@draw-guess/shared`）

- **协议版本**：`PROTOCOL_VERSION` 由 `'17'` 升到 `'18'`（不兼容变更，客户端必须同步）。
- **房间阶段**：`RoomPhase` 追加接龙专属阶段 `relay_choose` / `relay_draw` / `relay_guess` / `relay_showcase` / `relay_vote`；合法转换链为
  `starting → relay_choose → relay_draw(步1) → relay_guess(步2) → relay_draw(步3) → relay_guess(步4) → relay_showcase ⇄ relay_vote → game_result → waiting`
  （`paused` 在接龙不可达——接龙禁用暂停）。（S10 / S22 / S23 / S19）
- **步骤标识**：接龙用「**每步一个全局步骤 id**」承载既有协议里的回合 id 字段；服务端据「观看者 + 步骤 id」解析该玩家本步负责的链画布。（S53）
- **房间设置**：删除 `maxPlayers` 与 `joinPolicy`；新增接龙三时长（选词/作画/猜词），其合法档位为**白名单**（10/15/20/30、60/90/120/150、30/45/60/75，默认 20/90/45）；`gameMode` 放到**房间顶层**（与可见性同级、创建后不可变）。（S39 / S28 / S61 / S36）
- **新增请求事件 8 条**：5 条接龙绘图（笔画批次 / 填充提交 / 撤销 / 重做 / 清空，字段用步骤 id）、2 条提交（提交答案带文本、提交作画只标记完成）、1 条**独立聊天**（仅接龙使用，经典保持「猜词未命中即聊天」的现状）。（S51 / S30 / S79 / S85）
- **快照**：房间快照新增可选 `relay` 字段承载接龙视图（经典 `game` 字段与既有门禁路径完全不动）；接龙视图按观看者下发**最小集**（阶段、步骤、阶段时间、本链产物、我是否已提交、复盘期的链序号/半场/双胶囊内容/匿名票行）；大厅房间行新增模式标识、移除人数上限字段。（S57 / S63 / S67 / S80）
- **接龙视图不下发**的内容（隐私硬约束）：其余链的画作与答案、未揭晓的当前半场答案（含其长度）、任何玩家的恢复令牌与候选词池。（S35 / S63）
- **共享错误码**：接龙相关拒绝复用既有错误码体系（非法阶段 / 非法转换 / 已提交 / 未到你的棒次 / 版本冲突等），新增码必须先登记到唯一错误码表。

### 服务端领域（服务端权威）

- **接龙秘密状态**：新增接龙局状态与链状态两类秘密对象——局状态持有阶段时序、当前步骤 id、链数组、复盘游标与主计时器；链状态持有发起人、**两幅画布**、四棒产出与自己的票。**成员状态对象零新增字段**：提交与投票的权威记录全部挂在接龙结构上，左侧面板的「已提交/已投票」在快照期派生。（S56 / S64 / S45）
- **接龙状态机**：新增与经典回合状态机**平级**的接龙状态机（开局、选词、作画、猜词、步骤结算与换手、复盘轮播推进、投票结算、终局、代交兜底），只依赖窄端口、不反向依赖整机服务；装配层按房间模式委托给其一。（S55 / S1 / S22 / S23）
- **绘图内核**：把绘图的九个不变量（序号单调、历史只增不删、命令/点数/填充预算、撤销重做栈、清空、同步游标）抽成**纯函数内核**，经典与接龙共用；原绘图服务退化为「会话解析 + 预算门禁 + 注入发布策略」的薄协调层，**发布策略**由模式决定（经典=全房广播；接龙=**不广播**，仅写入链内权威历史）。（S49 / S2）
- **画布预算**：每幅画独立计数（命令数 / 点数 / 填充次数三档上限），每链两幅画各自独立。（S45）
- **步骤推进与秒切**：全员提交（选词后切入作画，作画步与猜词步全员提交）即取消剩余倒计时并推进；选词超时**随机代选**，作画/猜词超时按代交规则兜底。（S40 / S8 / S16）
- **掉队容错**：断线 20 秒宽限内重连可续当前步；超宽限或本步倒计时先到即代交；离开或长期掉线者仍占链位、后续每步代交；可玩人数 < 4 不中途中止。（S7 / S8 / S29 / S36 连带）
- **复盘推进**：按链发起人席位顺序逐条轮播；每半场「重播 → 停顿 → 揭晓」，两条半场后进入该链投票；展示期完全不可干预（无跳过、无提前结束），成员变动不中止轮播；对局期房主仍可提前结束。（S11 / S12 / S43 / S34 / S38）
- **投票结算**：只有赞同/不赞同；点下锁定；无弃权（未投计不赞同）；**一律等满 10 秒**；「赞同 > 反对」判为匹配成功，成功后该链 4 名参与者每人得「赞同票数 × 10」；离局者同样按未投处理。（S13 / S14 / S21）
- **房主可改字段白名单**：`updateSettings` 对模式不生效的字段**严格拒绝**（返回非法设置错误），沿用版本乐观锁。（S52 / S68）
- **开局门禁**：接龙要求在线可玩 ≥ 4 且全员准备；门槛常量进共享协议常量。（S62）
- **成员事实与阶段事实**：为接龙阶段补齐「对局中/可暂停/可结算」与「阶段标称时长」的既有单一口径；`isInMatchPhase` 必须包含接龙阶段，否则大厅会把接龙房间误显示为「房间中」。
- **快照门禁（客户端）**：按模式分流——接龙比较步骤 id + 画布修订 + 状态版本；经典分支不动。（S60）

## Testing Decisions

**好测试的标准**：只断言**外部可观察行为**——请求的 ack 结果、服务端推送的载荷、快照的可见字段、界面上的可读文案与可交互结果；
不断言私有字段、内部调用次数、组件内部状态，也不为「实现细节」写回归（如某个私有方法被调用了几次）。

**测试缝（全仓库只新增 1 个）**：

1. **接龙装配缝（新增）**：在既有「整机服务 + 假运行时」缝之上，新增一个**接龙局装配件**——一次调用即得到「4 人接龙房 + 词库 + 已开局」，并能把该局**推进到指定幕**（第 N 棒 / 复盘的某条链某半场 / 投票中 / 终局）。
   它复用既有的假时钟、内存仓储、迷你词库与测试 Socket，**不新建第二套替身**；建局的模式分支、玩家就位、开局门禁都由它统一处理，避免每个用例各写一遍。
2. **服务端整机缝（复用）**：驱动接龙状态机走完整局，断言 ack 与推送。
3. **角色裁剪快照矩阵（扩维度）**：现有矩阵是「角色 × 阶段」，接龙需扩为「角色 × 接龙阶段 × 步骤」并覆盖「链归属」维度（本链发起人 / 上家 / 无关链 / 已离局），同时把接龙的新秘密键登记进矩阵的禁止键清单。
4. **协议边界缝（复用，自动纳入）**：新增的 8 个请求事件的 schema↔响应契约配对、错误码穷尽、以及客户端请求边界扫描；这些测试由注册表驱动，新事件漏登记会直接失败。
5. **客户端组件缝（复用）**：顶栏两种形态、玩家 chip（角标语义）、作答浮层、投票卡（两答案底色一致、票行无底色）、玩家状态行。
6. **客户端集成缝（复用）**：接龙 store + 快照门禁接龙分支；**聊天与作答互不串**（聊天走独立事件、作答不出现于聊天流）。
7. **端到端缝（复用）**：1 条接龙全流程（4 人开局 → 四步 → 复盘轮播 → 投票 → 终局），用隔离的临时数据库与词库；顶部约定复用既有 launcher，不新增第二套装配。

**要覆盖的行为清单**（对应上文用户故事，不逐条重复）：

- 阶段与步骤推进：四步顺序、每步全员各动手一次、全员提交秒切、选词超时随机代选；
- 锁定与代交：重复提交被拒、断线与宽限、超时代交内容（画=已有笔画 / 猜=输入框内容或「？」）、离开者占位代交、人数 < 4 不中止；
- 隐私：观看者只见本棒所需内容；无关链内容、未揭晓答案与其长度都不进快照；对局期的绘图包不广播；
- 复盘时序：轮播顺序、每半场三段时长、展示期不可干预、成员变动不中止；
- 投票与计分：无弃权、等满倒计时、严格多数阈值、按票数 ×10 的入账、失败得 0、离局者按未投；
- 终局：只含排名与分数、行内为接龙统计、无称号、战报模式列写入 `relay`；
- 门禁与设置：在线可玩 ≥ 4 + 全员准备才能开局、开局后不可加入、模式不生效字段被拒、容量固定；
- 复用不回归：经典模式的阶段流转、快照、猜词与聊天在改造后行为不变（既有测试全绿即为此目的）。

**类似测试的先例**：接龙单测照 `test/unit/` 里既有的状态机与计分测试写法（假时钟 + 整机装配 + 断言 ack/推送）；
快照照 `test/unit/snapshot.matrix.spec.ts`；客户端照 `test/component/` 与 `test/integration/`；端到端照 `test/e2e/specs/` 里既有的全流程用例。

## Further Notes

- **先决顺序建议**：① 全局性删除（观战/候场/人数上限）独立一刀 → ② 协议层 → ③ 服务端领域（含迁移）→ ④ 客户端复用改造与接龙组件 → ⑤ 测试与文档。这样每一刀都能独立跑绿。
- **风险最高的三处**，实现时优先安排评审：
  1. **全局删除**触面很广（协议、房间设置、成员状态、快照、等待页、邀请容量、`rematch`、以及一批既有测试与专题文档），要先跑一遍受影响的测试清单再动手；
  2. **绘图发布策略分流**（经典广播 / 接龙不广播）是这次唯一改动生产热路径的地方，必须保证经典的绘图与重连行为逐条不变；
  3. **复盘轮播的时序**是「不可干预 + 精确 24 秒/链」，N=6 时全场约 144 秒，实现时确认服务端计时与客户端动画都以服务端时间为准。
- **UI 真值来源**：视觉与交互细节以原型分支为准（顶栏两形态、四元组不移动、投票卡形态、终局版式、房间头徽标）；实现时照抄其标记与类名，但**不要**把原型代码搬进主干。
- **共识中两条容易被忽视的细节**：复盘顶栏未揭晓的占位必须是经典遮罩同款下划线（不是问号）；投票卡的两个答案底色必须一致。
- **验收口径**：既有测试全绿 + 新增接龙测试通过 + 1 条接龙 e2e 通过 + 生产构建产物中不含原型代码。
