# 0058 接龙模式：服务端权威推进、策略分流与插槽式复用

**状态**：已采纳

- 来源：接龙模式（传话接龙）实施规格 `.scratch/relay-mode/spec.md` 与共识 `.scratch/relay-mode/consensus.md`（S1–S86）

## 背景

房间原本只有一种玩法（经典模式：轮流当画家、一轮一题），而规则里长期留着三样没人用的开关——观战、下一局加入、可调人数上限——它们让席位、加入流程与快照裁剪多出大量近乎不可达的分支。

我们想加第二种玩法「接龙模式」，它和经典模式有三处根本不同：

1. **没有「等别人画完」的串行**：N 名玩家并行开 N 条链，每条链固定 4 步（画 → 猜 → 画 → 猜），每步全员同时各对自己负责的那条链动手一次；
2. **保密是玩法的核心**：玩家只能看到自己本棒需要看到的东西（自己的候选与画布、或上家的画、或上家的答案），作答在揭晓前对其他人完全不可见；
3. **复盘与投票是长时序的**：四步走完后全员统一步调进入复盘轮播（每条链两个半场，每半场「重播 → 停顿 → 揭晓」），再对「初始词与最终答案是否匹配」投票。

如果按「经典模式加几个 if」来实现，会同时踩三个坑：把两个状态机揉成一个（经典的回归路径被污染）、把发布策略写进绘图热路径（隐私靠客户端自觉）、把两套 UI 并排复制（永久需要同步）。

## 决策

### 1. 服务端权威推进，两个状态机平级并存

接龙另建与经典回合状态机**平级**的状态机（开局、选词、作画、猜词、步骤结算与换手、复盘轮播推进、投票结算、终局、代交兜底），只依赖窄端口、不反向依赖整机服务；装配层按房间模式委托给其一，经典路径逐条不变。

- 阶段白名单在共享协议里扩展为 `relay_choose` / `relay_draw` / `relay_guess` / `relay_showcase` / `relay_vote`，合法转换链为 `starting → relay_choose → relay_draw(步1) → relay_guess(步2) → relay_draw(步3) → relay_guess(步4) → relay_showcase ⇄ relay_vote → game_result → waiting`（接龙禁用暂停，故 `paused` 不可达）。
- **步骤 id 承载回合 id 字段**：接龙用「每步一个全局步骤 id」，服务端据「观看者 + 步骤 id」解析该玩家本步负责的链画布；客户端不需要知道链的拓扑。
- **全员提交即秒切**：不把「等满倒计时」当默认节奏；倒计时只作兜底（选词超时随机代选、作画/猜词超时按代交规则补齐）。
- **成员状态零新增字段**：提交与投票的权威记录挂在接龙结构上，左侧面板的「已提交 / 已投票」在快照期派生——避免再长出一套与经典平行、需要永久同步的成员状态。

### 2. 绘图发布策略分流：唯一改动生产热路径的地方

把绘图的九个不变量（序号单调、历史只增不删、命令/点数/填充预算、撤销重做栈、清空、同步游标）抽成**纯函数内核**，经典与接龙共用；原绘图服务退化为「会话解析 + 预算门禁 + 注入发布策略」的薄协调层。

**发布策略由模式决定，单点注入**：经典＝全房广播（既有行为）；接龙＝**不广播**，命令只写入链内权威历史，由装配件注入静默实现。

- 这让「保密」由服务端结构保证，而不是靠客户端不发包；
- 代价是接龙客户端拿不到回推，本地镜像只能由提交 ack 自补（与服务端内核同口径），这部分记账集中在 `stores/relay.ts`，是接龙侧唯一需要小心的地方。

### 3. 按观看者最小集裁剪

接龙视图（快照里可选的 `relay` 字段）按「角色 × 接龙阶段 × 步骤 × 链归属」裁剪，只下发本棒所需内容；**绝不下发**其余链的画作与答案、未揭晓的当前半场答案（含其长度）、任何玩家的候选词池、恢复令牌与提交/投票归属。复盘期是公开复盘（全员同一份），但只公开游标当前那条链的当前半场。经典的 `game` 字段与既有门禁路径完全不动，接龙另走「**画布身份（步骤 id + 复盘游标）+ 画布修订 + 状态版本**」的门禁分支——**画布修订只在同一幅画布内可比**：复盘期的 `stepId` 在停机后不再变化，游标（链 + 半场）一切换，快照里就是另一幅画，而半场 2 常比半场 1 画得少；把两幅画的修订号拿来比较，整场复盘（含投票）会永久卡死在上一幅画上。这条口径由端到端验收抓到并钉进 `test/integration/snapshot-gate-relay.spec.ts`。

### 4. 计分与复盘时序单口径

- **计分**：每条链只有赞同 / 不赞同（无弃权、未投计不赞同）；**赞同严格多于反对**才判匹配成功，成功后该链 4 名参与者每人得「赞同票数 × 分值（10）」；失败得 0，不做归一化（每人参与链数恒为 4，同房比较公平）。
- **投票时长固定 10 秒、一律等满**：即使全员投完也不提前公布，保证断线的人有完整补投窗口；「少几张票」不会变相放宽阈值。
- **复盘每链 24 秒**：两个半场各「重播 3 + 停顿 1 + 揭晓 3」共 14 秒，加投票 10 秒；四时长是固定常量、房主不可改，服务端权威计时与客户端动画共用同一份配置，改配置即两端同步改变。复盘纯自动：不提供跳过、也不能提前结束，成员变动不中止轮播。

### 5. 插槽式复用，不并排复制组件

接龙与经典的差异一律通过**改造原组件 + 插槽 / props** 表达，经典不传新数据时行为与现状逐像素一致：

- 顶栏组件新增 `leading` / `center` 插槽（接龙传入「模式 + 阶段 + 棒次 / 链条进度」与「上一家 chip + 单个答案 UI」，复盘期为四元组「画家 chip + 答案 A → 答案 B + 猜词者 chip」）；
- 选词遮罩复用同一张选词卡标记（圆底图标 + 标题 + 换一批 / 自定义 + 黄底候选词大按钮），接龙只是全员各选自己那条链的词；
- 聊天面板新增聊天语义 props（接龙的标题与占位、提交目标改为独立聊天事件）；
- 玩家面板新增状态插槽（已提交 / 未提交 / 已投票 / 未投票）；
- 共用「玩家 chip」（头像 + 昵称 + 按条件显示的画笔角标，角标语义＝这一段里谁动笔画了）与拖动外壳；
- 终局复用经典结算版式，行内第二行换成接龙口径统计、去掉荣誉称号（接龙猜词不判对错，经典统计无数据源）。

### 6. 聊天与作答分离

接龙新增**独立的聊天事件**，聊天是自由社交频道、永远不携带作答内容；作答走两条专用提交事件（提交答案带文本、提交作画只标记完成），不进聊天流、不给其他人任何提示。经典模式保持「猜词未命中即聊天」的现状不变（本次不把经典切到独立聊天事件）。

### 7. 实现期修订（与设计文档的偏差，已登记）

以下三条是实施期对设计文档的修订，不改写历史决策，在此登记：

1. **S16 的一半分支不可实现**：共识 S16 说「猜词代交＝当前输入框内容，未输入则『？』」，但协议没有承载未提交草稿的通道、且接龙请求事件被冻结为固定条数；经用户拍板**收敛为固定兜底文本**（`RELAY_AUTO_SUBMIT_GUESS_TEXT`，位于 `apps/server/src/domain/relay/relay-steps.ts`，并留了可替换的单点 seam）。**该常量取值于 2026-10-05 按玩家可读性口径从「？」改为「上家未作答」**（读者须知见 `consensus.md` §十一「实现期修订」）。
2. **接龙请求事件实际为 9 条**（不是规格 §2.6 / §5.1 写的 8 条）：投票必须有入口，实现期新增 `relay:vote`（已登记事件名 / 请求 Schema / ack / 处理器 / 协议守卫测试）。`PROTOCOL_VERSION` 保持 `'18'`——该事件与初版契约同批发布，未产生额外的线上不兼容窗口。
3. **S52（服务端严格拒绝模式不生效字段）** 在规格 §5.2 未指派工单，由实现期的房间三幕改造一并落地：`MODE_SETTINGS_KEYS` 单一来源 + `updateSettings` 白名单 + 两端一致性单测。

## 后果

- 经典模式的回归面**零改动**：既有阶段流转、快照、猜词与聊天测试全部保持绿，是「平级状态机 + 策略注入 + 插槽复用」这三条约束的直接收益；
- 接龙把三种「不该给别人看」的东西（其他链的产物、未揭晓答案、作答草稿）都关在服务端，客户端拿到的即最小集；代价是复盘与投票的时序完全由服务端计时驱动，端到端用例必须真等满「每链 24 秒」；
- 复盘期的链数与半场进度、终局排名与统计都从接龙视图下发，经典与接龙共用同一套终局版式与退出状态机；
- 删除观战 / 候场 / 下一局加入与可调人数上限是一次**不可逆收缩**：容量固定 6 人、开局后不可加入，大厅、席位与快照少掉一整类分支（与接龙同批落地，避免留下「配置里有、永远不会用」的死字段）。
