# 架构决策记录（ADR）

本目录记录**已经落地、且单看代码看不出理由**的决策：为什么这样修、当时否掉了什么、代价是什么。
目的只有一个——让源码里那句「为什么」有地方可查，而不是指向一份会过期的审查编号。

## 什么时候写 ADR

- 修掉一个「反直觉但有原因」的缺陷，且未来很容易被「顺手改回去」；
- 在两个都可行的方案之间做过取舍（选了 A，就要写清为什么不是 B）；
- 引入了跨模块的约定（协议、渲染模型、持久化边界、命名等）。

日常小改动、纯重构、文档修订**不需要** ADR。

## 命名与结构

- 文件名：`NNNN-<kebab-case-英文短名>.md`，编号四位递增、不复用；
- 正文固定四段：**状态 / 背景 / 决策 / 后果**（外加「关联」列出代码与原始审查条目）；
- 状态只有三种：`已采纳` / `已废弃（被 NNNN 取代）` / `已推翻`；
- 决策一旦写进 ADR 就**不再改写历史**：改主意时新开一条并标注取代关系。
