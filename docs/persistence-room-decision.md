# 运行期房间持久化结论

## 结论

选择 **A：删除运行期房间写穿及相关回滚，只保留玩家短期身份和完成局战报**。

不选择 B（等待房间跨重启恢复），因为当前协议、领域模型和产品说明都把房间视为进程内权威状态；没有明确需求要求恢复等待房间。实现 B 还需要定义重启后的成员在线性、房主接管、私密房码、准备状态、Socket 订阅和恢复期限，属于新的产品语义，而不是对现有持久化的简化。

## 现状审查证据

改造前的 `rooms` / `room_members` 具有以下特征：

- 建房、加入、离开、房主迁移、规则及词库变更会调用 `saveAggregate`，属于只写路径；
- 唯一读取 `listRooms` 的生产代码位于 `recoverOnStartup`，读取结果后立即逐条 `removeRoom`；
- 启动代码没有把房间记录映射回 `RoomSecret`、`DomainContext.rooms` 或 Socket 房间，损坏的房间 JSON 也不会被解析；
- 玩家恢复只通过 `players.findByToken` 重建身份，并明确回到大厅；完成局战报独立存放在 `game_archive` / `game_results`。

因此，原实现承担了运行期写放大和失败回滚复杂度，却没有提供任何恢复能力。

## 落地边界

- 房间、成员席位、私密房码、准备状态、规则选择和对局状态仅保存在内存；
- `players` 只保存短期身份、恢复令牌、资料、偏好和断线宽限信息，不再读写运行期 `roomId`；
- `game_archive` / `game_results` 的完成局战报保持不变；
- 迁移 `remove-transient-room-storage` 只清空旧版 `players.room_id` 并删除遗留 `room_members` / `rooms` 表，不修改战报表；
- 静态边界测试禁止生产代码重新引入房间仓储或聚合写穿。

## 回归覆盖

- 房间成员契约测试证明加入流程不触达身份或战报仓储；
- 会话恢复测试继续约束“同一 UUID、回到大厅”；
- 房间阶段、断线与 E2E 测试继续覆盖原有行为；
- 迁移测试从包含旧房间数据和既有战报的 v4 数据库升级，断言遗留房间表删除且战报保留。

本次按任务要求不执行测试；仅执行类型、格式和差异检查。
